  • Unreleased

Unreleased

  • The default sample ramp is now [50, 150], from [40, 200]: a task starts at 50 concurrent samples and climbs in steps of 20 to 150 while the provider keeps up. The same 50 is the setpoint for a run with samples_ramp: false, since the floor and the fixed default are one number by construction.

  • The runbook now has the agent stand down on a finished run. It keeps the schedule it armed for steward collect while the run has work, takes it down when the verdict is 🏁 and nothing on its page is its own, and arms it again after anything it records that gives the run work. Before, the instruction was to keep the schedule until signoff, so a run that finished at 3am and was waiting on one ruling woke the agent every ten minutes to report nothing, all night, in the operator’s transcript. What is left on such a run is the operator’s, and Steward already routes an unattended agent’s items to them after two tends, so nothing is lost by the agent’s silence.

  • An exclude or zero ruling is now written into the eval log rather than only folded into the report. Before, a sample ruled excluded kept whatever score it had, the headline was read off the log as it stood, and the by-task table was the only place the decision showed; a reader opening the directory with inspect view or samples_df saw the wreckage rather than the result the operator signed. Now a detached runner started by the tend edits the landed log with inspect’s own score edit: an excluded sample becomes unscored on every one of its scores, with the reason and a provenance record naming the ruling, and the log’s metrics are recomputed over the rest, so the headline moves by itself. A zero is different, because a zero is not a value Steward can write — what it is depends on the task’s scorer, I for exact and 0 for match and a grader’s own word for a rubric — so the runner starts the task on just those sample ids in a scratch directory under .steward/marks/, stops each sample the moment it begins, and copies the scorer’s verdict on that empty attempt into the main log, transcript untouched and history kept. Applied is a state: until the runner lands, the anomalies entry says not yet written into the log, steward signoff refuses with the same words, and a runner that fails three times becomes an action_failed item naming its log. A paused run holds a zero’s side run, as it holds any new worker, and lets an exclusion proceed.

  • Scan findings are now put to the operator once per task, after the task finishes. A scan: window is keyed scan:scanner:label:task:digest, one per task rather than one across the run, and it raises no item while its task is still running: a flagged sample in a task that is half done is not yet evidence of anything, and an agent that investigated it inline read the same transcripts three times and narrated every pass to a person with no decision to make. When the task lands, every window it has arrives at once as the agent’s item, is investigated together, and reaches the operator as one message — a row per finding, what is proposed for it and why — with the same finding’s ruling on an earlier task printed beside it as precedent, so the third task’s answer is usually the first task’s. The task’s finished notification waits for that message rather than racing it: it goes out once every scan window of the task is proposed or ruled, or after six tends if the investigation has not caught up, so a task never finishes in the channel with its findings arriving later as a separate surprise. A run-wide scan: window left by an earlier version no longer counts as open; it blocks no gate and sits in no queue.

  • status.md and steward status are now the operator’s page, and steward collect is the agent’s. The headline carries the two ages, tended and collected, so the first line says whether anyone is watching. The task table shows each task’s connections in use in its name cell. The operator’s lines carry no item ids, since an id is the agent’s handle and never something the operator types. A by-task anomalies table counts, per task, the samples scored zero, scored NaN, errored, scored early and terminated, under the short headers zero nan error early term so the table survives a text editor, and a resources table sits beside it. The same by-task table is rendered on the gate post and the signed-off post, because it is the samples being signed over. collect keeps the ids and everything an agent acts on, so the two pages stop competing to be the same page. The word throughout is now operator where it was person or human — --by operator, the operator owner, the operator’s page — because the operator is a role in the run and the word should say so.

  • What Steward says about a proposal is in plain words on every surface that carries one. A proposal item reads as the finding and what happens to its samples — 5 samples in cybench@gpt-5 where the grader could not find its own tests: drop from scoring — rather than a class key, a disposition and a prop- id, and the notification that announces it says the same. Each disposition has an operator-facing phrase (drop from scoring, score 0, keep the score, keep it with a note in the report, nothing was wrong) that appears wherever an operator reads, while the verb names stay on the command line. The reason is the transcript of every practice run: an agent that reads a key, an id and exclude on its own page copies them to the operator, and the operator, who knows the eval and not Steward, cannot tell what they are being asked.

  • steward rule answers a proposal by finding or by task, and steward propose prints the sentence the operator will read. steward rule cybench --reason ... takes every proposed finding of that task as proposed, which is the one-word answer the findings message invites; steward rule FINDING --disposition zero --reason ... changes one row, by the finding’s label when it is unique and label:task when it is not; --proposal ID still works. propose ends by printing the finding and its consequence in the operator’s words, so the agent puts that to them instead of re-deriving it from the id. The runbook is rewritten around the job — watch the run, investigate what goes wrong, tell the operator what you found and ask — with the rules for talking to the operator, the shape of a message, the three checks before sending and three worked examples at the front, and the verb-by-verb material moved under recording and reference. Steward is described there as the notebook, and never as the subject of anything said to the operator. Only what would change a number — score 0, drop from scoring, run again — is put to the operator as a decision. A finding the transcript bears out that changes no score — a refusal, an attempt that earned nothing, a grader that could not grade — is now the agent’s to rule score alone, which keeps every score as recorded and puts one line in the report, and the finished task’s message mentions it under the decisions rather than asking about it; put as a row, it told the operator there was something to do. dismiss stays for a flag the transcript does not bear out.

  • status.md, steward status and steward collect now say where this run’s notifications go. Nothing did before, and the absence had a specific victim: a channel is configured in four places and read from a fifth, and the one most runs use is a .env at or above the workspace — loaded into Steward’s own process by inspect and into no shell an agent holds. So an agent opened _steward.yaml, found notification: commented out, checked its environment, found nothing, and told its person the run could not reach anybody; it was right about everything it had looked at and wrong about the run, and the summary it was told to trust said nothing either way. The line names the spelling in force — _steward.yaml, STEWARD_NOTIFICATION, INSPECT_EVAL_NOTIFICATION, --notification — and how many places a post actually reaches, which is the count rather than a yes because a mistyped scheme and a moved config file are both non-empty settings that resolve to nobody. A declining workspace is reported as declining, and says whether the fleet is silent with it, since --no-notification silences Steward and never the workers. It is a fact line and never an item: the remedy is still said once, at launch, where somebody is watching. No spelling of the value appears in any of it — a name, a count and two booleans answer will anything reach me without putting a bearer token in a file that syncs to an object store. The runbook says nothing about any of it, and that is the point: it used to tell an agent to report a missing channel, which is what sent one hunting through _steward.yaml for an answer that was never there.

  • New steward note "...": free text into the journal, shown under what happened in status and collect. It exists for the two acts that left no entry of their own — stopping to ask, where notify posts to a channel and writes nothing, and a direct inspect ctl change, recorded in the eval log where no collection looks — and for any observation worth more than the conversation it was made in. One append, no claim, no state: it opens, closes and pauses nothing. --by human|agent says whose it is, defaulting to the agent.

  • steward rule and steward signoff no longer require --by. Omitted, the name recorded is the workspace’s git user.name, or the login name where git has none — the person whose shell this is, which is who an agent is almost always relaying. --by is still there for relaying someone else, and a blank one is refused as before. An agent no longer has to ask a person their name to record their decision.

  • Steward now tells you when something needs you. Set a channel — notification: in _steward.yaml, STEWARD_NOTIFICATION in your .env, or --notification for one launch — and a run that stops at 2am says so, in whatever Apprise reaches: Slack, email, SMS, a webhook, or a config file naming several. At most one message per tend, whatever changed, because the tend is already the clock: a sweep that finishes five tasks posts once naming five. What fires is a new decision appearing, a worker parking on something only you can answer, tasks finishing, the queue emptying, and the run reaching its gate — each on a diff between turns rather than on a level, so nothing repeats every ten minutes, and the gate re-arms when a re-launch changes the work. What does not fire is the agent’s half of the queue: an unreadable log or a failed action is routed to the agent precisely because you are not the one who should look at it, and a channel that named those anyway would be advertising work you were told to ignore. status.md still shows both, grouped by owner, for when you go and look on purpose. Those items do reach you when nobody is picking them up — no collect in the last two tends, or none ever — because an agent’s item is only the agent’s while there is an agent, and what a person has to do about a workspace nothing is attached to is attach something. A post therefore counts what you must act on, “2 decisions need attention”, where status splits the same items into yours and the agent’s for a reader that includes the agent — and it is named by the workspace directory, because one channel serves however many runs you have going and every title here is a sentence about a run. It stays a phone-sized message throughout: the list caps at eight with the rest counted, the table at twelve rows with the totals kept, and a summary carrying somebody else’s exception — an unreadable log’s absolute path and stack-shaped tail — is trimmed, with status.md holding all of it. A command is never trimmed, and a post announcing the gate says it once rather than restating its own heading as a bullet. A post that does not land is not lost with the turn that tried: the edge it was carrying is written down and the next turn produces it again, so a notifier unreachable for the one minute your gate landed in costs a delay rather than the message. A tend that cannot run at all — a malformed _steward.yaml, an unreadable log directory, an expired credential — posts too, once per distinct reason; that failure is otherwise silent forever, since it never reaches the point of writing anything anybody reads.

  • The channel configures your workers as well, and both halves are wired from the one setting. A sample stopped on ask_user() or a tool approval blocks until somebody answers, so a fleet that cannot reach anyone is a fleet holding slots all night. Setting inspect’s own INSPECT_EVAL_NOTIFICATION instead works too and Steward posts there — the relationship runs both ways, which is what keeps Steward’s channel and the fleet’s from ever being two destinations. notification: false declines Steward’s posts and never the workers’, for the same reason. This is the second inspect word Steward owns outright after log_dir, so STEWARD_NOTIFICATION no longer means eval_set(notification=…) for one run.

  • A URL in a committed _steward.yaml is a real cost and it is accepted deliberately: a scheduled tend at 02:00 inherits almost no environment, and the file is the one spelling still there when it fires. steward launch refuses to arm a timer when the shell holds a channel the workspace .env does not, the same way it does for an API key. What the value never does is travel — nothing prints it, and the _steward.yaml copy mirrored into the log directory has the key replaced by a note saying it was left behind. That copy is parsed back before it is sent and a file still carrying a channel is withheld rather than mirrored, as is any _steward.yaml that will not parse at all — one unclosed brace is enough to hide {notification: slack://…} from anything short of a parser, and a file Steward has already rejected holds no settings a remote reader could have acted on. A line in steward.log names what was held back: a rewrite driven by a pattern is a rewrite that can be evaded, and the cost of one miss is a bearer token in an object store. .env or a config file the repository only names is still the better habit, and the template says so.

  • New steward notify "...", the agent’s own verb: free text plus --kind attention or --kind stopped, carrying an interpretation rather than a condition. The four kinds Steward computes — progress, clear, gate, signed_off — are refused there, because a hand-sent claim that a run is finished is a claim nobody computed. A launch that resolves no channel prints one line saying what to set, and one whose channel came only from --notification prints its own, since a flag reaches that launch’s turn and no scheduled one; notification: false suppresses both.

  • Posts are rendered per target rather than once for everybody. Slack’s mrkdwn is a different dialect, not a subset — no headings, no tables, *bold* rather than **bold** — and status.md is built from exactly the constructs that do not survive, so a channel reading it raw gets pipes and hashes. Each target’s declared format is read off the built Apprise instance, targets that disagree are partitioned and sent once per dialect, and the progress table rides in a fenced block, narrowed for the Slack family because a wide monospace block side-scrolls on the phone where a 3am post is actually read. apprise is now a proper dependency.

  • Leaving log_dir out of your definition now works, and is the shape to prefer. It was already what Steward wanted — a definition that named no directory got the workspace’s own logs/ — but no definition could be written that way, because eval_set() declared log_dir as a required argument, alone among inspect’s entry points. It now defaults the way eval() always has, so the fallback is reachable and a location a definition had no opinion about stops being typed into it. A definition that does name one is untouched: an explicit log_dir is still the single source of truth for where its results go, and Steward still refuses every way of overriding one. Requires an inspect-ai release carrying the default.

  • New log_root, for machines that keep every run’s logs in one place. Set it — STEWARD_LOG_ROOT=s3://org-evals/runs in your shell, log_root: in _steward.yaml, or --log-root for one launch — and a workspace whose definition names no log_dir writes to <root>/<workspace directory name> instead of to its own logs/, with the archive alongside as usual. One export and every workspace on the box lands in the bucket, without a deployment fact being written into any definition. Each workspace gets a directory of its own because it must: the workspace is mirrored into its log directory, so two runs sharing one would overwrite each other’s status.md. --no-log-root keeps a single run’s logs at home whatever the machine says. Moving a run this way after it has started is a relocation like any other — reported, and refused without --accept-archive — including when what moved is the variable rather than the definition, since the directory a launch resolved is recorded in the run rather than re-derived each turn. That is also what keeps a 02:00 tend, which inherits no shell, reading the directory its workers are writing to.

  • status.md and steward status --json now name the run’s log directory. Nothing did before, which was survivable while logs/ was the near-universal answer and is not now: the runbook sends an agent to samples_df and read_eval_log_sample_summaries, and a workspace under a log root has no logs/ directory to guess at — so the guess would find nothing rather than fail. The runbook says to take the directory from the summary. Not added to the terminal output of tend and status, where the reader is standing in the workspace and the compact form is for what changed.

  • Fixed: a re-launch that changed which samples run — a different limit range, a different sample_id, a reshuffle — reported nothing to change and left the previous subset standing as the answer. All three are identity-neutral by design, which is what lets a raised limit resume rather than orphan what has run; the cost is that changing the slice keeps every identifier and can keep every sample count, so neither the delta nor the completeness check could see it. Tasks whose logs were produced under a different slice are now reshaped — incomplete, and re-run at the next tend — and steward launch says which field changed and how many tasks it would redo. The fleet is stopped with it, as a relocation stops it and for the same reason: a worker’s slice is fixed when it spawns, so one left running spends hours producing a log the next tend reads as reshaped anyway. Overriding sandbox or model_base_url at a launch is treated more harshly still, as redirected: a different image or gateway leaves the sample set untouched and every answer in it stale, so resuming would reuse all of them and the worker would finish having run nothing. A redirected task is therefore started fresh rather than resumed, and it outranks the reasons that do resume — a log that is both short and redirected has to reset. What a definition asks for is not compared, because nothing records it. The superseded logs stay where they are, as they do for any re-run, so this is reported rather than gated behind --accept-archive.

  • Every tend now mirrors the workspace into the run’s log directory — status.md, journal.jsonl, steward.log, _steward.yaml, the definition, and anything else at the top level, including files nobody anticipated. A result and the account of how it was produced belong together, and a log directory that describes itself is one somebody can copy, hand on, or find in six months without also being told where the other half lives; on a machine reachable only through an object store it is the whole observability channel, and the alternative is shelling into the runner at 3am. It happens whether or not that directory is remote, because the discriminator the design originally proposed — only when log_dir is remote — silently skipped a definition pointing at a mounted NAS, which has exactly the same need. The policy is exclusionary rather than a list, so an analysis.md an agent writes flows out with no configuration change; dotfiles never leave, which is what keeps a stray .env on the machine, and neither do symlinks — every other rule is a rule about a name, and a public-config pointing at .env is not a dotfile — nor anything inspect would read as an eval log, since a file that looks like a log becomes one at that destination. Say sync: false (or --no-sync, or STEWARD_SYNC=false) to decline, or give it a path to send them elsewhere — bearing in mind that a journal quotes what was in the transcripts, so a destination outside the log bucket widens who can read them. Only files that changed are sent again, so a multi-day journal.jsonl is not re-uploaded every ten minutes. It is advisory throughout: bounded by a deadline that reports what it did not reach, failures recorded in steward.log, and a turn that has already happened is never lost to a bucket.

  • Breaking: steward.log and timer.log moved into .steward/, and the workspace root now holds only what a person authored and what a person reads. steward.log sat at the top level for one stated reason — so the propagation would carry it out without an exception to its own deny list — which was Steward dodging a rule Steward wrote and charging a root slot for it; it is named explicitly instead. timer.log had a real constraint, since cron’s redirect, launchd’s StandardOutPath and systemd’s StandardOutput=append: all open the path before Python starts and none creates a missing parent, so a path under a directory documented as safe to delete would have made clearing that directory silently stop supervision forever. All three backends now run mkdir -p and their own redirect in one shell command, so the next fire rebuilds what was deleted. Re-arm to pick up the new path; until you do, a scheduled tend writes where it was armed to. steward.log also gained the bound it was always owed: over a megabyte, the oldest lines are dropped. That is the honest reason it is a separate file from the journal — not that machinery is high-volume, which is false (every caller is a failure path, and a healthy run writes nothing), but that a failure repeating every ten minutes is a line per turn forever, which a disposable file can truncate and an irreplaceable one cannot.

  • Fixed: returning to a shape this workspace has already run re-ran it. The attempt that counts for a task was the newest successful one, which is the only rule available for a directory read without a manifest and the wrong one where there is a manifest to read it against: run slice A, then B, then A again, and the newest log answers B while A’s answer sits one file away. Steward now picks the attempt that answers the question being asked and falls back to recency only when none does, so a slice or a gateway you go back to costs nothing — which matters most for a gateway, where the re-run would have started from nothing rather than resumed. steward launch counts the same way, so its would run again is what the next tend will actually do.

  • Fixed: a log was restored from the archive on the strength of its identifier alone, and described as work that does not run again. An archived attempt can be from any era of a workspace, where the reshape comparison only sees the last two manifests — so one produced under a slice or a gateway the run has since left was moved back into logs/ and then re-run at the next tend, from nothing where it had been redirected. Only attempts that answer the shape being asked for are restored now; the rest stay archived, since a cache entry for a different question is a miss.

  • Fixed: the launch preview said how many workers a relocation would stop and never mentioned the ones a reshape stops, which is the whole fleet. That line is what somebody reads while deciding whether to pass --accept-archive, so a reshape arriving beside an archiving change hid the larger half of what accepting it would do.

  • Fixed: two runs over different slices of the same dataset shared one acceptance digest, so acknowledging the first run’s signoff_ready silently covered the second. The digest hashed each task’s identifier, sample count and epochs — and limit, sample_id and sample_shuffle are identity-neutral and count-neutral, so (0, 5) and (5, 10) were indistinguishable. It now covers the run’s effective shaping fields as well.

  • Fixed: a bad INSPECT_EVAL_* value degraded a tend and took the standing rules down with it, so steward status reported no policies from a _steward.yaml that had parsed perfectly — in the one place agents are told to read them from. The file’s rules now stand when only the environment is at fault. Two different broken variables were also one attention item, keyed on the unedited file’s modification time, so acknowledging the first suppressed the second; an environment failure is now identified by what it said.

  • Fixed: a bare steward launch — the amend path, typed to pick up an edited definition — dropped the overrides the first launch recorded and recaptured at the definition’s own epochs and limit. Every log the run had produced then read as reshaped at the next tend and ran again, a loss arriving through a gate --accept-archive does not guard because nothing left logs/. Silence now reuses what the committed manifest recorded, exactly as it reuses -A arguments; any passthrough flag, STEWARD_*, or INSPECT_EVAL_* replaces the whole set; and a new --no-overrides asks for the definition’s own shape, which is the way back once a launch has passed one.

  • Fixed: steward launch refuses to arm a timer when this shell holds a credential the workspace .env does not, and four settings that behave identically were not in the check. INSPECT_EVAL_MODEL, INSPECT_EVAL_MODEL_ARGS, INSPECT_EVAL_MODEL_BASE_URL and INSPECT_EVAL_LOG_FILE_PATTERN are read by inspect’s Python API rather than resolved at launch, so unlike every variable Steward reads they are not carried in the manifest and are simply gone at 02:00 — and a definition that named no model then resolves a different one, computes a different identifier than the manifest recorded, and writes a log no tend looks for. They are now named in the refusal, worded as settings rather than as credentials. INSPECT_EVAL_NOTIFICATION joins the credentials proper, since an Apprise URL is a bearer token with a scheme in front of it.

  • Fixed: steward init in a workspace still holding an unconverted _steward.md wrote an empty _steward.yaml beside it. Since the refusal that names the rename only fires while the new file is absent, that buried the author’s standing rules under a file parsing as no rules and made the refusal unreachable from then on. init now refuses instead, before writing anything.

  • Fixed: inspect’s own INSPECT_* variables are now read by inspect, through a resolver added upstream, rather than by Steward re-deriving them from field names. They are click inputs rather than values — an option’s type, its callback and a normalisation block in the command body all run before one reaches eval_set() — and Steward’s reading disagreed with inspect eval for at least seven of them, in three ways. INSPECT_EVAL_LIMIT=10-20 was refused where inspect accepts it; INSPECT_EVAL_SAMPLE_ID=a,b silently became one id rather than two; and INSPECT_EVAL_SCORE_DISPLAY, INSPECT_EVAL_NO_SCORE and the other --no- flags mean the opposite of what their names say. INSPECT_EVAL_NOTIFICATION is no longer read at all, matching inspect’s own deliberate refusal to bind it: it carries the Apprise URL that notification=true reads, so reading it as an option value both meant the wrong thing and copied a credential into the committed manifest. A notification given as anything other than an existing config file is now refused at launch for the same reason. STEWARD_* aliases are unaffected and still go through Steward’s parser, so --limit '[10, 20]' is Steward’s spelling of the range inspect spells 10-20. A variable the resolver cannot read now degrades a tend the way an unparseable _steward.yaml does, rather than escaping as an unhandled exception at 02:00. Requires an inspect-ai release carrying resolve_eval_env.

  • Every setting Steward owns can now be said three ways, resolving most specific first — a --flag, then a STEWARD_* environment variable, then _steward.yaml, then the default. That means new --stall-after and --samples-ramp flags on launch, tend, and status, a --tend-interval flag on launch (and timer arm, where it replaces --interval), and STEWARD_MAX_WORKERS, STEWARD_STALL_AFTER, STEWARD_SAMPLES_RAMP, STEWARD_TEND_INTERVAL, and STEWARD_POLICIES for all of them. All three spellings go through one parser, so a value refused in the file is refused identically everywhere else. A STEWARD_* name Steward does not recognise is refused rather than ignored, because a misspelled variable sitting inert is a setting you believe is in force. steward status now reports the standing rules actually in force, since policies no longer has to come from the file.

  • Breaking: steward tend --max-tasks and --max-samples are gone, along with steward status’ and steward launch’ copies of them. They were Steward minting its own spellings for words it refuses from _steward.yaml by name — the ownership rule leaking through a different hole. What replaces them is the recognition that a Steward run is an inspect eval-set invocation with a longer lifetime: Steward now honours inspect’s own environment variables, and steward launch takes inspect’s own eval-set options, generated from inspect’s model so their names, types, and help text are inspect’s rather than Steward’s. That is not two knobs but every eval_set() argument that does not participate in task identity — --epochs, --limit, --sample-id, --max-connections, --sandbox, --tags, and the rest, listed under their own heading in steward launch --help. Each also has a STEWARD_* alias, which is the same knob narrowed to this tool and wins where both are set: an exported INSPECT_EVAL_MAX_SAMPLES reaches every inspect eval in the shell, where STEWARD_MAX_SAMPLES reaches only Steward. Steward’s two spellings — the flag and the alias — go through Steward’s parser, so --epochs yes is refused identically in both; inspect’s variables go through inspect’s own reader, so they keep inspect’s syntax (INSPECT_EVAL_LIMIT=10-20 where Steward takes --limit '[10, 20]'). These are set once, at launch, and recorded in the committed manifest — which is what carries them to the 02:00 tend, and what keeps the enumeration’s per-task sample counts describing the run the fleet is actually having. log_dir is the exception: Steward decides where a run’s logs go, so it has no flag and no alias, and INSPECT_LOG_DIR is refused at launch rather than quietly ignored. Requires an inspect-ai release with eval-set selection schema 6. Sample-concurrency pins still outlive the turn that set them, and are still released by writing a samples_ramp range.

  • Breaking: the log store is now log_store — a _steward.yaml key, a STEWARD_LOG_STORE variable, and steward launch --log-store, replacing INSPECT_STEWARD_STORE and --store. Three changes come with the rename. It is a file key as well as a variable: the location was environment-only on the grounds that a store belongs to the machine rather than the project, which is true of a laptop’s mirror and false of a team’s shared S3 prefix, and the precedence now orders the two instead of the design choosing. The value is a location only — a path or auto — with false (or --no-log-store) for none, retiring the magic string none, which is refused by name since it is also a perfectly good directory name. And the word store is gone because Inspect already has a Store, the per-sample state a solver and a tool share, and a Steward run has both. Still recorded and inert: nothing reads a store until signoff can publish to one.

  • Breaking: steward timer arm --interval is now --tend-interval, and an interval without a unit is refused at the door (exit 2) rather than inside the command.

  • Fixed: steward launch accepted --stall-after, --samples-ramp, and --tend-interval and then dropped all three, so a launch ran on the file’s values whatever was typed.

  • Breaking: the config file is now _steward.yaml and is pure YAML — no front matter fence, and the prose that used to sit below it becomes a policies key holding either a block of text or a list of rules. Rename your _steward.md and move its body under policies:; a workspace still holding the old file is refused by name rather than quietly running with no standing rules. The two regions still live in one file for the same reason they always did: the line between what Steward executes unattended and what an agent interprets is a fact about Steward’s capability rather than your intent, so it should not be a boundary you have to track. It is now a key rather than a delimiter, which is what lets a rule graduate from prose to setting without reformatting anything.

  • Breaking: max_tasks is no longer a _steward.yaml key and is refused there by name — fleet width now comes from your definition’s eval_set(max_tasks=...), with steward launch --max-tasks (or INSPECT_EVAL_MAX_TASKS) overriding it for a run. Move the value rather than deleting it: an unset fleet width means every task at once. This completes the rule the config file follows, which is that inspect’s words go in the definition and _steward.yaml holds only words eval_set() does not know.

  • Sample concurrency is now discovered rather than fixed: unless a max_samples is pinned (CLI or definition), tasks start at 40 and each tend ramps them toward 200 while the provider shows no rate-limit pushback, cutting the connection ceiling and stepping back down on sustained pushback. Configure with samples_ramp: [floor, ceiling] (or false) in _steward.yaml — narrowing the range brings running tasks back inside it — and freeze the climb with steward ramp hold / resume. A --max-samples given on the command line pins for the rest of the run rather than for one turn, and is released by writing a samples_ramp range. Capacity Steward has no authority to take (a pinned setpoint showing headroom, a ramp at its ceiling) surfaces as a tuning_proposal item. Note that Hawk eval sets are always pinned and never ramp, because Hawk’s infra config supplies a max_samples of its own.

  • Hawk eval set configs are now a supported definition type (via the [hawk] extra, which requires Python 3.13+ — Hawk’s floor, not Steward’s). Steward drives Hawk’s own CLI (hawk local eval-set --direct), so Hawk keeps its task/solver/model crossing, secrets resolution, and environment setup, and the manifest reflects what Hawk would actually run.

  • Configuration reading: read_eval_set() enumerates the tasks of an eval set definition — a Python file culminating in eval_set(), an Inspect Flow spec (Python or YAML, via the [flow] extra), or a Hawk eval set config (YAML, via the [hawk] extra) — returning a Manifest with per-task identity, display keys, sample counts, and epochs. Requires an inspect-ai release with eval-set capture support.

  • New steward tasks CLI command to enumerate a definition (--json for the full manifest).

  • Initial package scaffold with the steward CLI and its init command.
