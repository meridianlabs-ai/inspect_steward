## Unreleased

- Fixed: a re-launch that changed **which** samples run — a different `limit` range, a different `sample_id`, a reshuffle — reported *nothing to change* and left the previous subset standing as the answer. All three are identity-neutral by design, which is what lets a raised limit resume rather than orphan what has run; the cost is that changing the slice keeps every identifier and can keep every sample count, so neither the delta nor the completeness check could see it. Tasks whose logs were produced under a different slice are now `reshaped` — incomplete, and re-run at the next tend — and `steward launch` says which field changed and how many tasks it would redo. The fleet is stopped with it, as a relocation stops it and for the same reason: a worker's slice is fixed when it spawns, so one left running spends hours producing a log the next tend reads as `reshaped` anyway. Overriding `sandbox` or `model_base_url` at a launch is treated more harshly still, as `redirected`: a different image or gateway leaves the sample *set* untouched and every answer in it stale, so resuming would reuse all of them and the worker would finish having run nothing. A redirected task is therefore started fresh rather than resumed, and it outranks the reasons that do resume — a log that is both short and redirected has to reset. What a definition asks for is not compared, because nothing records it. The superseded logs stay where they are, as they do for any re-run, so this is reported rather than gated behind `--accept-archive`.

- Fixed: returning to a shape this workspace has already run re-ran it. The attempt that counts for a task was the newest successful one, which is the only rule available for a directory read without a manifest and the wrong one where there is a manifest to read it against: run slice A, then B, then A again, and the newest log answers B while A's answer sits one file away. Steward now picks the attempt that answers the question being asked and falls back to recency only when none does, so a slice or a gateway you go back to costs nothing — which matters most for a gateway, where the re-run would have started from nothing rather than resumed. `steward launch` counts the same way, so its *would run again* is what the next tend will actually do.

- Fixed: a log was restored from the archive on the strength of its identifier alone, and described as work that does not run again. An archived attempt can be from any era of a workspace, where the reshape comparison only sees the last two manifests — so one produced under a slice or a gateway the run has since left was moved back into `logs/` and then re-run at the next tend, from nothing where it had been redirected. Only attempts that answer the shape being asked for are restored now; the rest stay archived, since a cache entry for a different question is a miss.

- Fixed: the launch preview said how many workers a *relocation* would stop and never mentioned the ones a reshape stops, which is the whole fleet. That line is what somebody reads while deciding whether to pass `--accept-archive`, so a reshape arriving beside an archiving change hid the larger half of what accepting it would do.

- Fixed: two runs over different slices of the same dataset shared one acceptance digest, so acknowledging the first run's `signoff_ready` silently covered the second. The digest hashed each task's identifier, sample count and epochs — and `limit`, `sample_id` and `sample_shuffle` are identity-neutral *and* count-neutral, so `(0, 5)` and `(5, 10)` were indistinguishable. It now covers the run's effective shaping fields as well.

- Fixed: a bad `INSPECT_EVAL_*` value degraded a tend and took the standing rules down with it, so `steward status` reported no policies from a `_steward.yaml` that had parsed perfectly — in the one place agents are told to read them from. The file's rules now stand when only the environment is at fault. Two different broken variables were also one attention item, keyed on the unedited file's modification time, so acknowledging the first suppressed the second; an environment failure is now identified by what it said.

- Fixed: a bare `steward launch` — the amend path, typed to pick up an edited definition — dropped the overrides the first launch recorded and recaptured at the definition's own `epochs` and `limit`. Every log the run had produced then read as `reshaped` at the next tend and ran again, a loss arriving through a gate `--accept-archive` does not guard because nothing left `logs/`. Silence now reuses what the committed manifest recorded, exactly as it reuses `-A` arguments; any passthrough flag, `STEWARD_*`, or `INSPECT_EVAL_*` replaces the whole set; and a new `--no-overrides` asks for the definition's own shape, which is the way back once a launch has passed one.

- Fixed: `steward launch` refuses to arm a timer when this shell holds a credential the workspace `.env` does not, and four settings that behave identically were not in the check. `INSPECT_EVAL_MODEL`, `INSPECT_EVAL_MODEL_ARGS`, `INSPECT_EVAL_MODEL_BASE_URL` and `INSPECT_EVAL_LOG_FILE_PATTERN` are read by inspect's Python API rather than resolved at launch, so unlike every variable Steward reads they are not carried in the manifest and are simply gone at 02:00 — and a definition that named no model then resolves a different one, computes a different identifier than the manifest recorded, and writes a log no tend looks for. They are now named in the refusal, worded as settings rather than as credentials. `INSPECT_EVAL_NOTIFICATION` joins the credentials proper, since an Apprise URL is a bearer token with a scheme in front of it.

- Fixed: `steward init` in a workspace still holding an unconverted `_steward.md` wrote an empty `_steward.yaml` beside it. Since the refusal that names the rename only fires while the new file is absent, that buried the author's standing rules under a file parsing as *no rules* and made the refusal unreachable from then on. `init` now refuses instead, before writing anything.

- Fixed: inspect's own `INSPECT_*` variables are now read by **inspect**, through a resolver added upstream, rather than by Steward re-deriving them from field names. They are click *inputs* rather than values — an option's type, its callback and a normalisation block in the command body all run before one reaches `eval_set()` — and Steward's reading disagreed with `inspect eval` for at least seven of them, in three ways. `INSPECT_EVAL_LIMIT=10-20` was refused where inspect accepts it; `INSPECT_EVAL_SAMPLE_ID=a,b` silently became one id rather than two; and `INSPECT_EVAL_SCORE_DISPLAY`, `INSPECT_EVAL_NO_SCORE` and the other `--no-` flags mean the *opposite* of what their names say. `INSPECT_EVAL_NOTIFICATION` is no longer read at all, matching inspect's own deliberate refusal to bind it: it carries the Apprise URL that `notification=true` reads, so reading it as an option value both meant the wrong thing and copied a credential into the committed manifest. A `notification` given as anything other than an existing config file is now refused at launch for the same reason. `STEWARD_*` aliases are unaffected and still go through Steward's parser, so `--limit '[10, 20]'` is Steward's spelling of the range inspect spells `10-20`. A variable the resolver cannot read now degrades a tend the way an unparseable `_steward.yaml` does, rather than escaping as an unhandled exception at 02:00. Requires an `inspect-ai` release carrying `resolve_eval_env`.

- Every setting Steward owns can now be said three ways, resolving most specific first — a `--flag`, then a `STEWARD_*` environment variable, then `_steward.yaml`, then the default. That means new `--stall-after` and `--samples-ramp` flags on `launch`, `tend`, and `status`, a `--tend-interval` flag on `launch` (and `timer arm`, where it replaces `--interval`), and `STEWARD_MAX_WORKERS`, `STEWARD_STALL_AFTER`, `STEWARD_SAMPLES_RAMP`, `STEWARD_TEND_INTERVAL`, and `STEWARD_POLICIES` for all of them. All three spellings go through one parser, so a value refused in the file is refused identically everywhere else. A `STEWARD_*` name Steward does not recognise is **refused rather than ignored**, because a misspelled variable sitting inert is a setting you believe is in force. `steward status` now reports the standing rules actually in force, since `policies` no longer has to come from the file.

- **Breaking:** `steward tend --max-tasks` and `--max-samples` are gone, along with `steward status`' and `steward launch`' copies of them. They were Steward minting its own spellings for words it refuses from `_steward.yaml` by name — the ownership rule leaking through a different hole. What replaces them is the recognition that **a Steward run is an `inspect eval-set` invocation with a longer lifetime**: Steward now honours inspect's own environment variables, and `steward launch` takes inspect's own eval-set options, generated from inspect's model so their names, types, and help text are inspect's rather than Steward's. That is not two knobs but **every `eval_set()` argument that does not participate in task identity** — `--epochs`, `--limit`, `--sample-id`, `--max-connections`, `--sandbox`, `--tags`, and the rest, listed under their own heading in `steward launch --help`. Each also has a `STEWARD_*` alias, which is the same knob narrowed to this tool and wins where both are set: an exported `INSPECT_EVAL_MAX_SAMPLES` reaches every `inspect eval` in the shell, where `STEWARD_MAX_SAMPLES` reaches only Steward. Steward's two spellings — the flag and the alias — go through Steward's parser, so `--epochs yes` is refused identically in both; inspect's variables go through inspect's own reader, so they keep inspect's syntax (`INSPECT_EVAL_LIMIT=10-20` where Steward takes `--limit '[10, 20]'`). **These are set once, at launch, and recorded in the committed manifest** — which is what carries them to the 02:00 tend, and what keeps the enumeration's per-task sample counts describing the run the fleet is actually having. `log_dir` is the exception: Steward decides where a run's logs go, so it has no flag and no alias, and `INSPECT_LOG_DIR` is refused at launch rather than quietly ignored. Requires an `inspect-ai` release with eval-set selection schema 6. Sample-concurrency pins still outlive the turn that set them, and are still released by writing a `samples_ramp` range.

- **Breaking:** the log store is now `log_store` — a `_steward.yaml` key, a `STEWARD_LOG_STORE` variable, and `steward launch --log-store`, replacing `INSPECT_STEWARD_STORE` and `--store`. Three changes come with the rename. It is a **file key** as well as a variable: the location was environment-only on the grounds that a store belongs to the machine rather than the project, which is true of a laptop's mirror and false of a team's shared S3 prefix, and the precedence now orders the two instead of the design choosing. The value is a **location only** — a path or `auto` — with `false` (or `--no-log-store`) for none, retiring the magic string `none`, which is refused by name since it is also a perfectly good directory name. And the word `store` is gone because Inspect already has a `Store`, the per-sample state a solver and a tool share, and a Steward run has both. Still recorded and inert: nothing reads a store until signoff can publish to one.

- **Breaking:** `steward timer arm --interval` is now `--tend-interval`, and an interval without a unit is refused at the door (exit 2) rather than inside the command.

- Fixed: `steward launch` accepted `--stall-after`, `--samples-ramp`, and `--tend-interval` and then dropped all three, so a launch ran on the file's values whatever was typed.

- **Breaking:** the config file is now `_steward.yaml` and is pure YAML — no front matter fence, and the prose that used to sit below it becomes a `policies` key holding either a block of text or a list of rules. Rename your `_steward.md` and move its body under `policies:`; a workspace still holding the old file is refused by name rather than quietly running with no standing rules. The two regions still live in one file for the same reason they always did: the line between what Steward executes unattended and what an agent interprets is a fact about Steward's capability rather than your intent, so it should not be a boundary you have to track. It is now a key rather than a delimiter, which is what lets a rule graduate from prose to setting without reformatting anything.

- **Breaking:** `max_tasks` is no longer a `_steward.yaml` key and is refused there by name — fleet width now comes from your definition's `eval_set(max_tasks=...)`, with `steward launch --max-tasks` (or `INSPECT_EVAL_MAX_TASKS`) overriding it for a run. Move the value rather than deleting it: an unset fleet width means every task at once. This completes the rule the config file follows, which is that inspect's words go in the definition and `_steward.yaml` holds only words `eval_set()` does not know.

- Sample concurrency is now discovered rather than fixed: unless a `max_samples` is pinned (CLI or definition), tasks start at 40 and each tend ramps them toward 200 while the provider shows no rate-limit pushback, cutting the connection ceiling and stepping back down on sustained pushback. Configure with `samples_ramp: [floor, ceiling]` (or `false`) in `_steward.yaml` — narrowing the range brings running tasks back inside it — and freeze the climb with `steward ramp hold` / `resume`. A `--max-samples` given on the command line pins for the rest of the run rather than for one turn, and is released by writing a `samples_ramp` range. Capacity Steward has no authority to take (a pinned setpoint showing headroom, a ramp at its ceiling) surfaces as a `tuning_proposal` item. Note that Hawk eval sets are always pinned and never ramp, because Hawk's infra config supplies a `max_samples` of its own.
- Hawk eval set configs are now a supported definition type (via the `[hawk]` extra, which requires Python 3.13+ — Hawk's floor, not Steward's). Steward drives Hawk's own CLI (`hawk local eval-set --direct`), so Hawk keeps its task/solver/model crossing, secrets resolution, and environment setup, and the manifest reflects what Hawk would actually run.
- Configuration reading: `read_eval_set()` enumerates the tasks of an eval set definition — a Python file culminating in `eval_set()`, an Inspect Flow spec (Python or YAML, via the `[flow]` extra), or a Hawk eval set config (YAML, via the `[hawk]` extra) — returning a `Manifest` with per-task identity, display keys, sample counts, and epochs. Requires an `inspect-ai` release with eval-set capture support.
- New `steward tasks` CLI command to enumerate a definition (`--json` for the full manifest).
- Initial package scaffold with the `steward` CLI and its `init` command.
